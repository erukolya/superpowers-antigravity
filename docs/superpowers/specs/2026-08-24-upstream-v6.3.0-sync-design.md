# Upstream v6.3.0 Sync — Design Spec

> Approved design for porting the portable half of obra/superpowers v6.3.0 into the
> Antigravity fork, shipping as v6.3.0. Ten content changes across six files, plus
> release chores. The multi-platform half of upstream's release is out of scope by charter.

## Approach

**Single combined release (v6.3.0).** Upstream's v6.3.0 landed as one squashed release
commit (`b36e082`): 40 files, +2888/-73. Roughly two thirds of that is new-harness
plumbing this fork exists to not carry. The remaining substance is eight prose changes and
two bug fixes, none of which this fork has.

**Grouped by file, not by upstream concern.** Four separate upstream changes all land in
`skills/subagent-driven-development/SKILL.md`; splitting them into four tasks would put
four implementers in one file for no review benefit. Trivial mechanical changes batch into
single tasks — which is what this release's own newly-ported guidance tells a controller
to do.

**Divergences are documented, not silent.** This fork's standing rule is that upstream
cherry-picks are word-for-word unless a divergence is recorded in the plan doc and the
commit message. Four divergences below meet that bar.

## Task 1: Brainstorming Three-Path Router

**File:** `skills/brainstorming/SKILL.md`

### Problem

Every request currently walks the full nine-step architectural checklist: questions,
approaches, sectioned design, written spec, then writing-plans. A feasibility probe and a
one-line flag change pay the same ceremony as a new subsystem. Upstream's #2063 fixes this
by classifying the request first.

### Changes

1. **Add a Three Paths section** after the HARD-GATE, classifying each request as
   **spike** (a feasibility question whose output is an answer, not kept code),
   **bounded** (a well-scoped change to a flow that already exists in this repo), or
   **architectural** (new projects, new subsystems, interface changes). The agent announces
   the classification out loud before its first question so the human can override it.
2. **Rewrite the HARD-GATE** so the gate is approval, not the design artifact: ceremony
   scales with the task, the approval gate never does.
3. **Replace the "Too Simple To Need A Design" anti-pattern** with "Too Simple To Need
   Approval", making explicit that what scales with simplicity is the artifact.
4. **Add the Red Flags table** (7 rows) covering the rationalizations that let an agent
   downgrade its own path.
5. **Split the checklist into three path-specific checklists.** Spike is 5 bare steps.
   Bounded is 5 steps ending in implementation with no plan document. Architectural keeps
   the existing 9 steps unchanged.
6. **Extend the process-flow digraph** with the classification diamond, the two new
   terminal states, and the one-way upgrade ratchet.
7. **Scope the terminal-state paragraph** and the `## After the Design` heading to the
   architectural path.

### Divergence from upstream

Upstream's patch cannot be applied word-for-word. This fork's checklist already carries
native steps that upstream's does not: `task.md` artifact tracking, `generate_image` at
step 2, and `TypeName: "research"` for parallel context exploration. Upstream's
architectural checklist still says "offer the visual companion", which this fork removed
in v6.0.0.

The merge rule for the new paths:

- **Spike** — bare. No `task.md` artifact, no visual step. Artifact ceremony on a
  three-sentence probe is precisely the over-ceremony the router exists to remove.
- **Bounded** — keeps `task.md` tracking, and keeps `generate_image` available, since
  small UI changes benefit from a cheap mockup.
- **Architectural** — unchanged from the current fork text.

### What stays the same

- The HARD-GATE's position and force — only its wording changes
- The architectural path's nine steps, spec self-review, and user review gate
- `generate_image` as the visual mechanism (no browser companion, no consent gate)
- `TypeName: "research"` for parallel exploration

## Task 2: SDD — Rulings, Scan Table, Batching, Finish Report

**File:** `skills/subagent-driven-development/SKILL.md`

### Problem

Four related upstream changes, all addressing controllers that stall or waste dispatches.
Upstream reports one donated session that sat blocked for almost nine hours on a question
the controller could have decided itself.

### Changes

1. **Rulings, not stalls** (#2077). Replace open-ended escalation with a recorded ruling:
   the spec is the binding authority, the plan is its argument, and the controller's
   judgment settles what neither answers. Every decision goes to the ledger as
   `Ruling: <what> — <why> — <cost if wrong>`. Exactly four things stop the controller: an
   irreversible or destructive operation, a security-sensitive action, a side effect
   outside the worktree that norms say to ask about first, and a plan so broken every path
   forward is a guess. Three current sites change, anchored by their present text (line
   numbers as of this spec, and they will shift as edits land):

   - L14, the continuous-execution paragraph — "The only reasons to stop are: BLOCKED
     status you cannot resolve, ambiguity that genuinely prevents progress, or all tasks
     complete."
   - L209, the review loop's plan-mandated finding — "and the plan text, ask which
     governs."
   - L254, the breaker's load-bearing branch — "**Real and load-bearing** — the task is
     BLOCKED: stop and present it to..."

   The digraph's "Ask human partner which governs" and "STOP: report BLOCKED" nodes change
   with them. The fourth "which governs" site at L125 belongs to change 2 below, not here.
2. **Conflict scan records its checks** (#2080). The pre-dispatch scan's output becomes a
   table written to the ledger — one row per task pair sharing a file or interface, one row
   per task for internal self-agreement — not a bare "clean" assertion.
3. **Batch small same-shape work** (#2078). When the plan lists several small independent
   edits of the same kind, compose one dispatch brief listing every file and its change,
   and review the diff as one unit. One-dispatch-per-task is reserved for work needing its
   own judgment, tests, or review surface.
4. **Spec pointer read at setup** (#2086). If the plan names a Spec, read it too; conflicts
   inside the plan resolve against it. A plan with no reachable spec gets a ledger note
   saying rulings made without one are provisional.
5. **Rulings surfaced at Finish.** Before deleting the workspace, collect every ledger line
   containing `Ruling:` into the final message under "Rulings I made", in order, each with
   what it costs if wrong. A ruling that dies with the workspace was a decision made in
   secret.

### Divergence from upstream

Upstream's re-review paragraph cites `scripts/review-package PLAN_FILE FIX_BASE HEAD`.
This fork does not ship `skills/subagent-driven-development/scripts/` — upstream's helper
scripts hand work over through gitignored files, which implementers running under
`Workspace: "branch"` cannot read. Per the standing rule, port the problem statement and
re-express the mechanics natively. The same applies to any `task-brief` or `sdd-workspace`
reference in the ported text.

### What stays the same

- The five-round fix cap and resume-based fix loop
- The per-plan ledger under `.superpowers/sdd/<plan>/`
- Model-selection guidance via agent-file frontmatter
- `send_message` for resuming idle implementers

## Task 4: Spec Reviewer — Illegible Evidence and Batch Verification

**File:** `agents/spec-reviewer.md`

### Problem

A reviewer that cannot read the implementer's test evidence re-runs the suite to regenerate
it. That is not verification — it replaces the claim under review with a fresh claim the
reviewer produced itself.

### Changes

1. **Illegibility is not invalidation.** Evidence you cannot see is not evidence that does
   not exist. Re-read the file at its stated path. If it is genuinely missing or garbled,
   report that as a gap for the controller. Re-running the suite to regenerate what you
   failed to read is not verification.
2. **Batched-dispatch check.** When the brief lists several files each with its own change,
   verify the diff file by file — a listed file the diff never touches is a **Missing**
   finding regardless of how clean the rest of the batch looks. This is what makes Task 2's
   batching safe to rely on.

### Divergence from upstream

Upstream puts both changes in `skills/subagent-driven-development/task-reviewer-prompt.md`,
a single reviewer prompt covering spec compliance and code quality. This fork split that
role in two and moved the system prompts into bundled agents: `agents/spec-reviewer.md` and
`agents/code-reviewer.md`, with the files under `skills/` reduced to dispatch templates.
Both changes are spec-compliance concerns, so both land in `agents/spec-reviewer.md`. The
dispatch templates are untouched.

## Task 5: Worktree Removal Refusal

**File:** `skills/finishing-a-development-branch/SKILL.md`

### Problem

Step 6 runs `git worktree remove "$WORKTREE_PATH"` unconditionally. When git refuses
because the tree holds modified or untracked files, the tempting next move is `--force`,
which permanently destroys files that exist nowhere else — uncommitted plans, notes,
scratch work.

### Changes

1. Add an **If removal is refused** branch after the removal command: never `--force` on
   your own initiative. Run `git -C "$WORKTREE_PATH" status --porcelain -uall`, show the
   file list, and offer three choices — commit to the branch, move to the main repo root,
   or delete (unrecoverable). Carry out the choice, then remove.
2. Add the matching Red Flags row: "Removal refused — `--force` is just finishing the
   cleanup" → the refusal means those files exist only there.

This applies to this fork unchanged: the platform-managed `Workspace: "branch"` path
already returns early, but the `.worktrees/` and `worktrees/` branch below it does run
`git worktree remove` and is exposed to exactly this failure.

## Task 6: render-graphs.js Bug Fixes

**File:** `skills/writing-skills/render-graphs.js`

### Problem

Two defects, both inherited from upstream and both fixed upstream in v6.3.0.

1. **The script cannot run at all.** It uses CommonJS `require()` at lines 16-18, while the
   repo root `package.json` declares `"type": "module"`. Node resolves module type from the
   nearest package.json walking up; neither `skills/` nor `skills/writing-skills/` has one,
   so the root applies and the file is treated as ESM, where `require` is undefined.
2. **`which dot` is not a command on Windows** (line 112). This fork ships PowerShell
   install instructions, so this reaches users directly.

### Changes

1. Convert to ESM: `import * as fs from 'fs'`, `import * as path from 'path'`,
   `import { execFileSync } from 'child_process'`.
2. Replace `execSync('dot -Tsvg', ...)` with `execFileSync('dot', ['-Tsvg'], ...)`.
3. Replace the `which dot` availability probe with
   `execFileSync('dot', ['-V'], { stdio: 'ignore' })`, carrying upstream's comment
   explaining why.

Both fixes are one file and mechanically identical in shape, so they batch into one task.

## Out of Scope

Recorded so the next reconciliation does not re-litigate these.

### Excluded by charter — multi-platform plumbing

`.devin-plugin/`, `.hermes-plugin/` (including `__init__.py` and `plugin.yaml`),
Codex/Cursor/Kimi manifest bumps, `references/hermes-tools.md`, the
`references/codex-tools.md` rewrite, `scripts/sync-to-codex-plugin.sh`, `bump-version.sh`
Hermes wiring, `.version-bump.json`, `tests/devin/`, `tests/hermes/`, and the
`hermes-tools.md` line added to the harness list in `using-superpowers/SKILL.md`.
Approximately 2,100 of the release's 2,888 added lines.

### Excluded — already solved, structurally

Upstream #2059 adds an identical **"You Do Not Dispatch Subagents"** block to four files:
`implementer-prompt.md`, `task-reviewer-prompt.md`, `re-review-prompt.md`, and
`requesting-code-review/code-reviewer.md`. It exists because on upstream's harnesses every
subagent inherits the full tool set, so reviewers were spawning their own reviewers and
duplicating a review seat per task.

This fork's bundled agents carry explicit `tools:` allowlists. `agents/code-reviewer.md`,
`agents/spec-reviewer.md`, and `agents/re-reviewer.md` each list `view_file`, `list_dir`,
`find_by_name`, `grep_search`, `run_command` — and `agents/implementer.md` adds only write
and web tools. None includes `invoke_subagent`. The capability is absent, so the prose has
nothing to prevent.

**Decision:** skip all four blocks. Do not add them "for safety" — roughly 40 lines of prose
guarding a tool the agents cannot call is exactly the dead weight this fork exists to shed.
State the reasoning in RELEASE-NOTES so it reads as a native-port result rather than an
oversight.

### Excluded — supersedes a divergence this fork already made

`skills/brainstorming/visual-companion.md`: upstream's change corrects Copilot backgrounding
guidance for the browser-based companion server. This fork removed that server in v6.0.0 in
favour of native `generate_image`, and does not ship the file.

## Implementation Order

1. **Task 6** — render-graphs fixes. Independent of everything, fixes live breakage.
2. **Task 3** — `Spec:` pointer. Three lines; Task 2 depends on it existing.
3. **Task 2** — SDD SKILL.md. The largest prose change; consumes Task 3.
4. **Task 4** — `agents/spec-reviewer.md`. Makes Task 2's batching safe to rely on.
5. **Task 1** — brainstorming router. Independent, but the highest-judgment merge; it
   benefits from going after the mechanical work has settled.
6. **Task 5** — worktree removal refusal. Independent.
7. **Task 7** — release chores. Last, so version and notes describe what actually landed.

## Verification Plan

**Gate — must pass before any commit:**

```
bash tests/antigravity/test-skill-tool-purity.sh
```

No legacy tool names, no legacy platform names, no tool-mapping references anywhere under
`skills/`. Ported upstream prose is clean of these, but Task 2's `scripts/review-package`
re-expression and Task 1's merged checklist are the two places where a careless port could
introduce a violation.

**Regression:**

```
bash tests/antigravity/test-agent-frontmatter.sh
bash tests/antigravity/test-plugin-discovery.sh
bash tests/antigravity/test-rule-sync.sh
```

Task 4 edits content adjacent to agent frontmatter and Task 7 edits manifests, so both
suites are load-bearing here.

**Per-task:** each prose task verifies by reading the changed section back against the
upstream text it ports, confirming the divergences listed in this spec are the only ones
present.

### Known verification gap

**Task 6 cannot be executed-tested in the current environment.** Node is not installed —
neither `node` on the Bash PATH nor as a PowerShell command. The ESM diagnosis is static
analysis (root `package.json` `"type": "module"` plus `require()` in a `.js` file with no
intervening package.json), and the fix matches upstream's, but it will ship unrun unless
node is installed first.

Do not report Task 6 as verified on the strength of the diagnosis. Either install node and
run `node skills/writing-skills/render-graphs.js skills/brainstorming` — expecting SVG
output, or a clean "graphviz (dot) not found" error if graphviz is absent, rather than a
`ReferenceError: require is not defined` — or record it in the ledger as fixed-but-unrun
and say so in the final report.
